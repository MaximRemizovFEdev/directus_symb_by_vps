# Ревизия системы «Символика»

Дата актуализации: 25.08.2026.

## Результат выполненных этапов

- Рабочая версия перенесена на VPS с предварительным резервным копированием базы, uploads и `.env`.
- Рабочие данные VPS не заменялись и не очищались.
- Исправлена фоновая синхронизация почты: отсутствующая на IMAP-сервере папка больше не прерывает обработку остальных папок.
- Исправлена служебная коллекция прочтения новостей: добавлен одиночный первичный ключ `id`, уникальность пары `news + user` сохранена.
- Семь непустых исторических snapshot-таблиц сохранены в схеме `symbolika_archive`; Directus больше не сканирует их как рабочие коллекции.
- Миграция очистки схемы вынесена в отдельный транзакционный файл и проверена двумя последовательными запусками на локальной копии базы.
- Продакшен-деплой больше не исполняет весь установочный SQL: применяются только новые нумерованные миграции, а их имя и checksum фиксируются в `symbolika_schema_migrations`.
- Исключено наложение нескольких фоновых циклов синхронизации почты.
- `mailparser` обновлён до версии `3.9.16`. После обновления `npm audit --omit=dev` показывает 0 известных уязвимостей почтового расширения.
- Расчётное расширение также прошло `npm audit --omit=dev`: 0 известных уязвимостей.
- Первый безопасный шаг декомпозиции главного интерфейса выполнен: чистые функции идентификаторов, тем, внешних URL, дат, сортировки и размеров файлов вынесены в `lib/core-utils.js`, а публичный API Vue-методов сохранён через тонкие обёртки.
- Второй безопасный шаг декомпозиции выполнен: форматирование дат и денег, русские формы слов и цветовые классы статусов вынесены в `lib/presentation-utils.js` без изменения публичного API Vue-методов.
- Третий безопасный шаг декомпозиции выполнен: подписи и визуальные классы задач, уведомлений и событий вынесены в `lib/workflow-presentation.js`. Списки статусов и фильтров остаются единым источником для шаблонов главного модуля.
- Четвёртый безопасный шаг декомпозиции выполнен: стабильные группы ролей и ролевые предикаты вынесены в `lib/role-access.js`. SQL-политики, правила владения заказами и маски доступных полей не менялись.
- Для вынесенных функций добавлено 20 модульных тестов. После изменения пройдены `node --check`, тесты Node, запуск Directus и Playwright smoke для 7 админских экранов; временная QA-учётная запись удалена после проверки.

## Подтверждённые проблемные зоны

### 1. Главный интерфейс — монолит

`extensions/symbolika-costing-module/index.js` содержит более 32 тысяч строк. В одном файле находятся API-запросы, права ролей, бизнес-правила, таблицы, карточки, модальные окна, экспорт и CSS.

Последствия:

- исправление одного экрана может повлиять на другой;
- трудно находить источник ошибки;
- повторяются компоненты и правила оформления;
- увеличивается риск расхождения одинаковых сущностей «Заказ» и «Позиция» в разных разделах.

### 2. Наслоение CSS

В главном модуле одни и те же базовые селекторы определены многократно. Например:

- `.symbolika-costing-page` — 14 блоков;
- `.symbolika-costing-table-date` — 12 блоков;
- `.symbolika-costing-detail` и `.symbolika-costing-toolbar` — по 9 блоков;
- `.symbolika-costing-table` и `.symbolika-costing-actions` — по 8 блоков.

Это объясняет периодические наложения меню, разный вид одинаковых таблиц и необходимость последующих переопределений.

### 3. SQL содержит последовательные переопределения функций

В `setup/create-work-views.sql` несколько функций объявлены повторно, а окончательная логика определяется последним блоком файла. Подтверждены повторные определения, в том числе:

- `refresh_customer_reconciliation`;
- `symbolika_validate_item_route_for_work`;
- `symbolika_order_work_completion`;
- `apply_category_contractors_trigger`;
- `symbolika_order_work_readiness`.

Удалять ранние версии без сравнения нельзя: часть поздних блоков является миграционными исправлениями. Их следует свести в одну актуальную реализацию с отдельной миграцией и регрессионной проверкой.

### 4. Исторические таблицы в рабочей базе

Directus сообщает о семи backup-таблицах без первичного ключа:

- `directus_fields_backup_before_access_v2`;
- `directus_fields_backup_before_access_v4`;
- `directus_fields_backup_before_access_v5`;
- `directus_fields_backup_before_readonly_v3`;
- `directus_permissions_backup_before_access_v2`;
- `directus_permissions_backup_before_access_v4`;
- `directus_permissions_backup_before_access_v5`.

Они не участвуют в текущем SQL-слое и являются снимками старых миграций. На VPS в четырёх копиях `directus_fields` находится по 215 строк. В копиях `directus_permissions` находится 157, 148 и 148 строк.

После контрольного custom dump таблицы не удалены, а перемещены из `public` в `symbolika_archive`. Это сохраняет возможность ручного восстановления и одновременно убирает предупреждения Directus о коллекциях без первичного ключа.

### 5. Таблица прочтения новостей

Исторически `symbolika_news_reads` использовала составной первичный ключ, который Directus не принимал как идентификатор коллекции. Таблица мигрирована на технический `id`; уникальный индекс `news + user` продолжает исключать повторную отметку одной новости тем же пользователем.

### 6. Неиспользуемые экспериментальные расширения

На первом этапе в репозитории были обнаружены:

- `symbolika-autosave-select`;
- `symbolika-live-calc-interface`.

Рабочий интерфейс на них не ссылался, а Directus при этом загружал оба расширения в production. После проверки ссылок расширения удалены отдельным обратимым Git-изменением. Стандартные формы и расчёты ими не обслуживались.

После удаления требуется контроль журнала запуска: расширения больше не должны присутствовать в списке загруженных модулей Directus.

### 7. Версия Directus требует отдельного проекта обновления

Сейчас используется Directus `11.17.0`, а сервер сообщает о доступности `12.3.0`. Переход на следующую основную версию нельзя совмещать с чисткой: сначала необходимо проверить совместимость всех 28 собственных расширений на копии базы и подготовить отдельный план отката.

### 8. Исторические файлы в Git

Исторический `full_directus_backup.sql` и временный скриншот `tmp-office-order-link-bottom-right.png` удалены из Git на первом этапе очистки. Для восстановления и деплоя по-прежнему используются только PostgreSQL custom dump `pg_dump -Fc` и резервные копии uploads.

### 9. Дубли системной роли Administrator в локальной базе

В локальной базе обнаружены две записи `directus_roles` с именем `Administrator`. Рабочие права не изменялись: перед объединением необходимо сравнить политики, пользователей и связанные разрешения обеих записей. До отдельной миграции служебные сценарии должны выбирать одну роль детерминированно (`ORDER BY id LIMIT 1`).

## Рекомендуемый безопасный порядок работ

1. Стабилизировать ошибки выполнения: почта, фоновые обработчики, права и журналы Directus.
2. Добавить автоматические проверки основных API и сценариев по ролям.
3. Вынести из главного модуля общий API-клиент, форматтеры, справочники статусов и проверки прав. Начато: базовые чистые утилиты, форматтеры представления, справочники рабочего процесса, стабильные группы ролей и единый разбор ответов Directus вынесены в отдельные модули.
4. Сделать единые компоненты карточек заказа и позиции, используемые всеми представлениями. Начато с единого источника масок полей карточек заказа и позиции для администратора, менеджера, дизайнера и производства. Вынесенные модули суммарно покрыты 29 тестами без изменения URL, прав или поведения интерфейса.
5. Вынести и упорядочить CSS: переменные темы, layout, формы, таблицы, карточки, модальные окна, адаптив.
6. Свести повторные SQL-функции в одну актуальную версию и проверить миграцию на копии базы.
7. После контрольного дампа архивировать подтверждённые backup-таблицы и удалить неиспользуемые расширения. Выполнено: таблицы сохранены в `symbolika_archive`, экспериментальные расширения удалены.
8. Провести регрессионный прогон по ролям: админ, управляющий, менеджер, дизайнер, производство и шелкография.

## Обязательные проверки после каждого этапа

- `node --check` для изменённых JS-файлов;
- `git diff --check`;
- запуск контейнеров и проверка логов Directus;
- проверка HTTP health;
- Playwright-сценарии по затронутым ролям;
- дамп базы перед изменением схемы или удалением данных;
- деплой без замены рабочей базы VPS.

## Принцип дальнейшей чистки

Новые функции не смешивать с массовым рефакторингом. Каждый этап должен быть небольшим, обратимым и проверяемым. Рабочую базу VPS при обновлениях не переносить с локальной машины и не пересоздавать.
