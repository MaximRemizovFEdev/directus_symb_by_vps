## Подтверждённые проблемные зоны

### 1. Главный интерфейс — монолит

`extensions/symbolika-costing-module/index.js` содержит более 32 тысяч строк. В одном файле находятся API-запросы, права ролей, бизнес-правила, таблицы, карточки, модальные окна, экспорт и CSS.

Последствия:

- исправление одного экрана может повлиять на другой;
- трудно находить источник ошибки;
- повторяются компоненты и правила оформления;
- увеличивается риск расхождения одинаковых сущностей «Заказ» и «Позиция» в разных разделах.

### 2. Наслоение CSS

В главном модуле одни и те же базовые селекторы определены многократно. Например:

- `.symbolika-costing-page` — 14 блоков;
- `.symbolika-costing-table-date` — 12 блоков;
- `.symbolika-costing-detail` и `.symbolika-costing-toolbar` — по 9 блоков;
- `.symbolika-costing-table` и `.symbolika-costing-actions` — по 8 блоков.

Это объясняет периодические наложения меню, разный вид одинаковых таблиц и необходимость последующих переопределений.

### 3. SQL содержит последовательные переопределения функций

В `setup/create-work-views.sql` несколько функций объявлены повторно, а окончательная логика определяется последним блоком файла. Подтверждены повторные определения, в том числе:

- `refresh_customer_reconciliation`;
- `symbolika_validate_item_route_for_work`;
- `symbolika_order_work_completion`;
- `apply_category_contractors_trigger`;
- `symbolika_order_work_readiness`.

Удалять ранние версии без сравнения нельзя: часть поздних блоков является миграционными исправлениями. Их следует свести в одну актуальную реализацию с отдельной миграцией и регрессионной проверкой.

### 4. Исторические таблицы в рабочей базе

Directus сообщает о семи backup-таблицах без первичного ключа:

- `directus_fields_backup_before_access_v2`;
- `directus_fields_backup_before_access_v4`;
- `directus_fields_backup_before_access_v5`;
- `directus_fields_backup_before_readonly_v3`;
- `directus_permissions_backup_before_access_v2`;
- `directus_permissions_backup_before_access_v4`;
- `directus_permissions_backup_before_access_v5`.

Они не участвуют в текущем SQL-слое и выглядят как следы старых миграций. Удалять их можно только отдельной операцией после контрольного дампа и проверки содержимого.

На VPS в четырёх копиях `directus_fields` находится по 215 строк. В копиях `directus_permissions` находится 157, 148 и 148 строк. Таблицы не пустые, поэтому автоматическое удаление в рамках первого этапа не выполнялось.

### 5. Таблица прочтения новостей

`symbolika_news_reads` использует составной первичный ключ. PostgreSQL работает с ним корректно, но Directus не считает такой ключ подходящим идентификатором коллекции и пишет предупреждение. Безопасное исправление — добавить технический `id`, сохранив уникальность пары `news + user`.

### 6. Неиспользуемые экспериментальные расширения

В репозитории остаются:

- `symbolika-autosave-select`;
- `symbolika-live-calc-interface`.

Рабочий интерфейс на них не ссылается, а документация запрещает включать их без отдельного тестирования. Перед удалением нужно проверить список реально загруженных Directus-расширений; затем убрать их отдельным коммитом.

Проверка журнала запуска подтвердила, что Directus сейчас действительно загружает оба расширения, несмотря на отсутствие рабочих ссылок на них. Это лишний исполняемый код в production, но удалять его следует только после короткой проверки стандартных форм и расчётов.

### 8. Версия Directus требует отдельного проекта обновления

Сейчас используется Directus `11.17.0`, а сервер сообщает о доступности `12.3.0`. Переход на следующую основную версию нельзя совмещать с чисткой: сначала необходимо проверить совместимость всех 28 собственных расширений на копии базы и подготовить отдельный план отката.

### 7. Исторические файлы в Git

В репозитории всё ещё отслеживаются `full_directus_backup.sql` и временный скриншот `tmp-office-order-link-bottom-right.png`. Дамп не должен использоваться для восстановления и деплоя: стандарт проекта — только PostgreSQL custom dump `pg_dump -Fc`.

## Рекомендуемый безопасный порядок работ

1. Стабилизировать ошибки выполнения: почта, фоновые обработчики, права и журналы Directus.
2. Добавить автоматические проверки основных API и сценариев по ролям.
3. Вынести из главного модуля общий API-клиент, форматтеры, справочники статусов и проверки прав.
4. Сделать единые компоненты карточек заказа и позиции, используемые всеми представлениями.
5. Вынести и упорядочить CSS: переменные темы, layout, формы, таблицы, карточки, модальные окна, адаптив.
6. Свести повторные SQL-функции в одну актуальную версию и проверить миграцию на копии базы.
7. После контрольного дампа удалить подтверждённые backup-таблицы и неиспользуемые расширения.
8. Провести регрессионный прогон по ролям: админ, управляющий, менеджер, дизайнер, производство и шелкография.

## Обязательные проверки после каждого этапа

- `node --check` для изменённых JS-файлов;
- `git diff --check`;
- запуск контейнеров и проверка логов Directus;
- проверка HTTP health;
- Playwright-сценарии по затронутым ролям;
- дамп базы перед изменением схемы или удалением данных;
- деплой без замены рабочей базы VPS.

## Принцип дальнейшей чистки

Новые функции не смешивать с массовым рефакторингом. Каждый этап должен быть небольшим, обратимым и проверяемым. Рабочую базу VPS при обновлениях не переносить с локальной машины и не пересоздавать.
