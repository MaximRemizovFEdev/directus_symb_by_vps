# Контекст проекта «Символика»

Этот файл нужен как короткая память проекта для Codex и будущих правок. Если чат становится слишком большим, сначала читать этот файл, затем точечно смотреть код.

## Главная идея

Система строится на Directus 11 + PostgreSQL как учетная система рекламно-производственной компании «Символика».

Directus используется как база, права, API и shell админки, но рабочие процессы постепенно переносятся в собственные интерфейсные модули. Стандартные коллекции Directus считаются техническим нижним уровнем; обычные пользователи должны работать через понятные разделы системы.

Основной локальный адрес:

```text
http://localhost:8057/admin/
```

Основные контейнеры:

```text
symbolika-directus
symbolika-db
```

## Git, дампы и деплой

- Живую базу `symbolika_directus_clean_install/database/` не коммитить.
- Для переноса базы использовать только PostgreSQL custom dump `-Fc`.
- Shell-скрипты `*.sh` должны храниться в LF, иначе на Linux Directus может не стартовать.
- Перед коммитом всегда смотреть `git status --short`.
- Не откатывать чужие незакоммиченные изменения без прямого разрешения.

Команды:

```powershell
node --check symbolika_directus_clean_install\extensions\symbolika-costing-module\index.js
cmd /c "docker exec -i symbolika-db psql -v ON_ERROR_STOP=1 -U directus -d directus < symbolika_directus_clean_install\setup\create-work-views.sql"

```

## Роли

- `Administrator` - полный доступ, видит все разделы, справочники, финансы, управление.
- `Управляющий` - видит общую картину, управление, себестоимость, производство, офис, заказы.
- `Менеджер` - видит свои заказы, своих клиентов и компании, может создавать заказы, позиции, оплаты, работать с офисной выдачей.
- `Офис-менеджер` - выдает заказы, меняет офисные статусы, принимает оплаты.
- `Производство` - видит только свои производственные позиции.
- `Шелкография` - видит только свои позиции шелкографии.
- `Контрагент` - задел под будущий кабинет контрагента.
- `Дизайнер` - рабочая роль: видит дизайнерские задачи по отмеченным позициям, ТЗ и заполняет ссылку на макет.

## Разделы интерфейса

Логика меню: страницы должны лежать в том разделе, где ими реально пользуются. Админу не надо дублировать все страницы в «Админку»; админ просто должен иметь доступ к тем же разделам.

Основные разделы:

- `Заказы` - сводка, очередь задач, задачи, проблемы, поиск, все заказы, мои заказы, сроки, расчеты, архив заказов и позиций.
- `Производство` - производство, шелкография, архив производства, этикетки и склад. Закупки создаются автоматикой и из рабочих сценариев, но единый список закупок здесь не дублируется.
- `Управление` - себестоимость, единый список закупок и контроль автоматизаций. Это каноническое место работы администратора и управляющего с закупками.
- `Финансы` - сверки, оплаты, показатели менеджеров.
- `Клиенты` - клиенты, компании, карточки и сверки.
- `Админка` - сотрудники, пользователи/роли, должности, справочники, маршрутизация, финансы админки, зарплаты, расходы, расчеты с контрагентами, финрезультат.

## UI-принципы

- Основной режим эксплуатации - темная тема.
- Стиль интерфейса: лаконичный, аккуратный, близкий к iOS/macOS: меньше шума, больше воздуха, понятные группировки, спокойные поверхности, читаемые таблицы.
- На экране не должно быть горизонтального скролла там, где можно разумно ужать колонки или объединить данные в многострочные ячейки.
- Таблицы должны быть плотными, но читаемыми.
- Операционные страницы поддерживают переключение `Таблица / Карточки / Канбан`; выбранный режим хранится отдельно для каждой страницы в браузере.
- В канбане задач карточки можно перетаскивать между колонками статусов.
- Статусы показывать русским текстом и цветными пинами/селектами.
- Номера заказов не должны быть лишними ссылками; заказ открывается кликом по свободной части строки.
- В таблицах можно объединять в одну ячейку несколько строк: номер заказа + дата + срок, заказчик + компания, менеджер + статус, деньги.
- Быстрая карточка справа должна показывать полезные данные без внутренних id.
- Карточки должны закрываться по крестику и по клику в свободную область вне карточки.
- Кнопки не должны вылезать за границы меню или таблиц.
- Нельзя оставлять белые системные dropdown в темной теме.

## Заказы и позиции

Позиция заказа является главным рабочим объектом для производства, себестоимости, ТЗ, сроков, статусов и маршрутизации.

Статусы заказов и позиций:

- Новый
- Согласование
- Доработка макета
- Отправлен в работу
- В работе
- Готов
- Доставлен / Выдан
- Отменен

Правила синхронизации:

- Если все позиции готовы, заказ становится `Готов`.
- Если заказ ставят `Готов`, все позиции становятся `Готов`.
- Если все позиции доставлены/выданы, заказ становится `Доставлен`/`Выдан`.
- Если заказ ставят `Доставлен`/`Выдан`, все позиции становятся выданными.
- Аналогично для `Отменен`.
- Если производство ставит `Доработка макета`, статус позиции тоже становится `Доработка макета`.
- Если производство ставит `Готов`, статус позиции становится `Готов`.
- Если у заказа есть срок, новая позиция должна получать этот срок по умолчанию, но менеджер может заменить его вручную.

## Офисная выдача

Офис работает по заказам, но при раскрытии заказа видит позиции и их офисные статусы.

Офисные состояния:

- к выдаче;
- в офисе;
- выданные;
- архив выдачи.

Правила:

- Если все позиции заказа в офисе, заказ получает офисный статус `В офисе`.
- Если хотя бы одна позиция не в офисе, заказ не должен считаться полностью в офисе.
- Если заказ выдан, все позиции выданы.
- Если позиция принята в офис или выдана, ее производственный статус автоматически становится `Готов`, независимо от забытого статуса участка.
- Уже доставленный заказ не может содержать позицию со статусом `В офисе`: такая позиция автоматически считается выданной.
- Выданные заказы уходят из активной выдачи в архив.
- Офис-менеджер может менять только офисный статус и принимать оплату.
- В офисной карточке нужна кнопка приема оплаты: сумма + тип оплаты во всплывающем интерфейсе.

## Оплаты и сверки

Клиент может заказывать лично или от компании.

Правило плательщика:

- Если в заказе выбрана компания, плательщик для сверки - компания.
- Если компания не выбрана, плательщик - клиент.

Расчеты:

- Сумма заказа считается по позициям.
- Оплачено считается по платежам и распределениям.
- Остаток = сумма заказа - оплачено.
- Частичная оплата распределяется по позициям сверху вниз.
- В сверке по позициям клиенту нужно видеть все позиции заказов, без внутренних производственных деталей.
- Экспорт сверки должен быть пригоден для отправки клиенту: дата сверки, менеджер, клиент, компания, затем строки заказов и позиций.

Нестандартные просьбы заказчиков учитываются отдельно от заказов в `customer_operations`. Это могут быть покупки на маркетплейсе, выдача/снятие наличных и прочие операции. Для каждой записи явно выбирается направление: `customer_owes_us` или `we_owe_customer`. Только статус `confirmed` влияет на баланс и попадает в общую сверку; черновики и отмененные записи финансового эффекта не имеют. Клиентские операции не считаются выручкой, заказом или оплатой и не участвуют в проценте менеджера.

Для переноса клиентов и компаний из прежней системы в `customers` и `customer_companies` есть поля `opening_balance_amount`, `opening_balance_direction`, `opening_balance_date` и `opening_balance_comment`. Сумма всегда вводится положительной, а направление определяет знак в сверке: `customer_owes_us` — клиент/компания должны нам, `we_owe_customer` — мы должны клиенту/компании либо у них есть аванс. Триггеры поддерживают ровно одну подтвержденную запись `customer_operations` с типом `opening_balance` на каждого клиента или компанию. Изменение полей обновляет эту запись без дублей, а сумма `0` удаляет ее финансовый эффект. Начальный остаток входит в общую сверку, но не считается заказом, оплатой, выручкой или базой для процента менеджера.

## Себестоимость и контрагенты

Себестоимость заполняют админ/управляющий.

В рабочем интерфейсе себестоимости нужны:

- заказ;
- позиция;
- подрядчик 1;
- себестоимость 1;
- подрядчик 2;
- себестоимость 2;
- итоговая себестоимость;
- прибыль;
- маржа.

Оплаты контрагентам:

- не считаются операционными расходами;
- закрывают долг перед контрагентом;
- себестоимость уже учтена в прибыли заказа.

Для контрагента с признаком `is_internal_production` (по умолчанию это `Собственное производство`) себестоимость подрядчика всегда равна нулю. Ненулевое значение обнуляется серверным триггером, а ноль считается корректно заполненной себестоимостью. Затраты внутреннего производства учитываются не как долг контрагенту, а отдельными операционными расходами.

В разделе расчетов с контрагентами есть два представления:

- `По контрагентам` — подрядчик, начислено по себестоимости, оплачено и общий долг;
- `По заказам` — заказ, заказчик, контрагент, позиции, начислено, оплачено и остаток;
- кнопка оплаты в строке заказа открывает существующую форму платежа с автоматически заполненными контрагентом, заказом и остатком;
- сумму можно изменить для частичной оплаты, а созданный платеж сохраняет привязку к заказу;
- платежи без привязки к заказу влияют на общий баланс контрагента, но не распределяются произвольно между заказами.

## Маршрутизация

Основной источник истины - `product_routing_rules`.

Логика:

```text
категория / подкатегория / вид нанесения -> подрядчик 1 / подрядчик 2
```

Не путать с историческими полями контрагента `default_product_category` и `default_product_subcategory`: они могут существовать, но не должны быть главным механизмом маршрутизации.

Производство и шелкография - внутренние участки, но технически могут использоваться как контрагенты/подрядчики.

Заказы попадают в производственные представления, когда позиция отправлена в работу и назначен соответствующий подрядчик/участок.

## Заготовки, склад и закупки

Для текстиля и сувенирки нужна логика заготовок:

- менеджер выбирает, нужна ли закупка заготовки;
- можно указать поставщика заготовки;
- можно указать себестоимость заготовки;
- вариант `заготовка заказчика` должен быть отдельным пунктом;
- вариант `со склада` не требует поставщика и не создает заявку на закупку;
- закупаемая заготовка создает строку в закупках.

Поставщики должны быть разделены по типу:

- поставщик текстиля;
- поставщик сувенирки;
- прочие поставщики.

В закупках:

- рабочим источником является `procurement_requests`; историческая витрина заготовок из `contractor_costing` не выводится отдельной страницей `Закупка`;
- страница `Закупки` показывается только в модуле `Управление` и не дублируется в заказах, производстве и админке;

- видно, что нужно заказать;
- указывается поставщик;
- есть галочки `заказано`, `получено`/`забрано`;
- нужна массовая отметка;
- после заказа может создаваться задача оплатить;
- после оплаты/готовности может создаваться задача забрать.

Для производства и шелкографии нужен склад расходки:

- бумага;
- тонер;
- пленки для ламинирования;
- пружины;
- краски;
- скотч;
- химия;
- прочие материалы.

Если у активной складской позиции остаток строго меньше минимального, система автоматически создает одну открытую заявку на закупку на разницу до минимума. Пока заявка имеет статус `Нужно заказать`, изменение остатка или минимума пересчитывает количество; при восстановлении остатка такая автозаявка отменяется. Уже заказанные заявки автоматически не отменяются.

Закупочную заявку может создать производство, шелкография или менеджер вручную; склад также создает ее автоматически по минимальному остатку. Открытые заявки автоматически объединяются в `procurement_batches` по поставщику и одинаковым условиям получения (способ доставки, транспортная компания, город и адрес). В одну группу могут входить складские материалы, ручные заявки и заготовки из разных заказов. Для группы создается одна задача типа `procurement`; одинаковые позиции в интерфейсе суммируются, но исходные заявки и их связь с заказами сохраняются. Перевод групповой задачи в `Готово` ставит группе и всем входящим заявкам статус `Заказано`. После заказа новые заявки того же поставщика попадают в новую открытую группу. Заказать группу без назначенного поставщика нельзя.

Управляющий видит все закупочные заявки в модуле `Управление` без ограничения по участку и имеет тот же рабочий доступ к заявкам и объединенным закупкам, что и администратор: создание, редактирование реквизитов и смена статусов.

У контрагента нужна локация/адрес и логика доставки:

- город;
- адрес/ПВЗ;
- нормативный срок готовности/забора;
- самовывоз;
- транспортная компания: СДЭК, Деловые линии и т.п.

## Таск-трекер

В системе нужен внутренний таск-трекер:

- задачи самому себе;
- задачи сотруднику;
- задачи по заказу/позиции;
- статус, приоритет, срок;
- фильтры: мои, назначены мне, поставил я, команда, просроченные, готово.

Автозадачи:

- заказать заготовку;
- оплатить поставщику;
- забрать заказ у поставщика;
- подготовить макет/дизайн;
- проверить заказ, требующий внимания.

## Лента событий

- `symbolika_event_feed` — рабочая, доступная по ролям проекция штатного аудита Directus для заказов, позиций и задач.
- Для событий изменения хранится `before_delta` — прежние значения измененных полей. Оно используется для точечного и последовательного отката.
- Откат выполняется через `/symbolika-event-rollback/rollback` с текущими правами пользователя и создает новое событие аудита.
- Источник истины — `directus_activity` + `directus_revisions`; триггер переносит безопасный набор изменений и связи в рабочую ленту.
- В карточке заказа показываются события заказа, его позиций и связанных задач; в карточках позиции и задачи — локальная история.
- Общая страница `Лента событий` поддерживает поиск, фильтр по объекту и действию, диапазон дат, экспорт и переход в связанную карточку.
- Администратор и управляющий видят всю ленту. Остальные роли получают только события своих заказов, задач, участков или дизайнерских позиций.
- Финансовые служебные поля себестоимости, прибыли, налогов и комиссии в `delta` ленты не сохраняются.

## Дизайнер

Реализованная логика:

- В Directus существуют отдельная роль `Дизайнер`, политика доступа к дизайнерским задачам и должность `Дизайнер` в справочнике сотрудников. Для корректного назначения сотруднику нужны и пользователь с этой ролью, и карточка сотрудника с этой должностью.
- В позиции заказа есть галочка `Нужна помощь дизайнера`.
- Если галочка включена, дизайнер видит задачу у себя.
- Дизайнер видит позицию, заказ, клиента/компанию, ТЗ, постановочный комментарий менеджера/производства и отдельную ссылку на исходный файл.
- Исходный файл и результат разделены: исходник не считается готовым макетом.
- Дизайнер вставляет ссылку на готовый макет в поле результата; дополнительные файлы можно прикладывать во вложениях задачи, а уточнения вести в обсуждении.
- У дизайнерской задачи есть статус: новая, в работе, нужны правки, готово.
- Если дизайнер ставит `Готово`, менеджеру приходит уведомление.
- При завершении задачи ссылка на готовый макет заменяет макет в позиции автоматически; без ссылки на результат завершить дизайнерскую задачу нельзя.
- После готовности макета менеджер может запускать позицию в работу.

## Финансы и зарплаты

Финансы админки:

- финансовый дэшборд;
- зарплаты;
- расходы;
- расчеты с контрагентами;
- финрезультат по месяцам.

Зарплата сотрудника:

```text
оклад + процент от заказов - выплаты/авансы
```

Проценты менеджерам считаются от оплаченной базы заказов согласно проценту в карточке сотрудника.

Расходы:

- аренда;
- зарплата;
- авансы сотрудникам;
- доставка;
- материалы производства: бумага, тонер и подобное;
- производственная расходка;
- обслуживание и ремонт техники;
- закупка прочих запасов;
- прочие расходы.

Оплата контрагентам - отдельный тип операции, который закрывает долг контрагенту и не должен второй раз уменьшать чистую прибыль.

Финрезультат:

- прибыль по заказам считается после себестоимости, процентов и налогов, но до операционных расходов;
- чистая прибыль равна прибыли по заказам минус операционные расходы, включая материалы, расходку, обслуживание техники и прочие запасы;
- показывать месяц, год, прошлый год;
- отдельно показывать текущий прогноз до конца месяца с учетом известных постоянных расходов.

- количество берется из позиции заказа.

## Контроль автоматизаций

Для администратора есть отдельный экран `Контроль автоматизаций`. Источник данных — служебная таблица `symbolika_automation_issues`, которую функция `refresh_symbolika_automation_issues()` пересобирает после изменений заказов, позиций, закупочных заявок, пакетов закупки и задач.

Контролируются три класса нарушений:

- итоговый статус заказа не соответствует совокупности статусов его позиций;
- активная закупочная заявка или пакет закупки остались без активной задачи на заказ;
- задача заказа/получения выполнена, но закупка не перешла в ожидаемый следующий статус.

Таблица доступна через API только политикам с `admin_access = true`. Позиции объединенной закупки не считаются закупками без задачи: общая задача хранится на пакете.

## Большие таблицы и пагинация

Растущие рабочие наборы в `symbolika-costing-module` загружаются через общий клиентский слой `loadPagedCollection()` порциями по 100 записей. Следующая страница Directus запрашивается заранее через `IntersectionObserver`, когда нижний маркер приближается к области просмотра. В интерфейсе показывается прогресс `загружено / всего` и остается ручная кнопка дозагрузки как запасной вариант.

Для строк таблиц, карточек, событий и групп закупки включена браузерная виртуализация через `content-visibility: auto` и резервный размер строки. Справочники, которые участвуют в обычных HTML-селектах, либо остаются небольшими, либо догружаются полностью последовательными пакетами, чтобы пагинация не скрывала варианты выбора.

## Заполнение заказов

Для администратора в заказах рассчитывается показатель `Заполнение`. Функция `symbolika_order_completion(order_id)` проверяет основные поля заказа и каждой позиции, включая контрагентов и их себестоимость. Результат (`completion_percent`, `completion_missing_count`, `completion_missing`) хранится в рабочих витринах заказов и автоматически пересчитывается триггерами при изменении заказа или позиции.

Подкатегория и вид нанесения считаются обязательными только если для выбранной категории существуют соответствующие варианты. Для позиции с дизайнерской задачей дополнительно проверяется ссылка на готовый макет.

## Совместная работа в задачах

В карточке сохраненной задачи доступны три связанных рабочих блока:

- чек-лист подзадач из `symbolika_task_checklist`;
- обсуждение с автором и временем сообщения из `symbolika_task_comments`;
- вложения Directus Files через связующую коллекцию `symbolika_task_attachments`.

Вложения загружаются из рабочего модуля, в интерфейсе действует ограничение 25 МБ на один файл и до 10 файлов за один выбор. Участники задачи — исполнитель и постановщик — получают доступ к связанным данным; администратор имеет полный доступ.

Отметка `Жду ответа` использует существующий статус задачи `waiting`. Повторное нажатие возвращает задачу в статус `in_work`, поэтому отдельное логическое поле для ожидания не создается.

## Жизненный цикл заказа

Для менеджера черновик заказа и его позиции имеют только статусы `Новый` и `Согласование`. Запуск выполняется отдельной кнопкой `Отправить в работу`, а не ручным выбором статуса. Кнопка появляется, когда в заказе есть позиции и заполнены все менеджерские поля. Себестоимость и контрагенты в эту проверку не входят и остаются частью админского показателя `Заполнение`.

Функция `symbolika_order_work_readiness(order_id)` является серверным источником истины. При первом запуске заказ и все его позиции переходят в `В работе`. После запуска менеджеру доступны целевые статусы `Готов` и `Доставлен`. Итоговый статус заказа пересчитывается из статусов позиций, а изменение итогового статуса заказа распространяется на позиции.

При переходе позиции в `Доработка макета` в `orders_items.layout_revision_url_snapshot` сохраняется прежняя ссылка. Повторный запуск разрешается только после изменения ссылки. При этом в работу возвращаются только позиции с правками; уже готовые позиции не откатываются.

## Передача клиентов и комиссий менеджеров

Ответственный за работу и получатель комиссии теперь разделены:

- `orders.manager_employee` и `orders_items.manager_employee` — текущий ответственный менеджер; это поле меняется при передаче клиента или компании;
- `orders.commission_manager_employee` и `orders_items.commission_manager_employee` — менеджер, создавший продажу и получающий процент; после назначения это поле неизменяемо;
- любой активный внутренний сотрудник может создать собственный заказ в разделе `Заказы -> Мои заказы`; система принудительно назначает его ответственным и комиссионным менеджером;
- процент берется из `employees.order_percent`, поэтому администратор может отдельно настроить ставку каждому сотруднику, независимо от его основной роли;
- для существующих заказов при миграции комиссионным менеджером зафиксирован менеджер, который вел заказ до появления этой логики;
- зарплатные и менеджерские финансовые сводки связывают заказ с `commission_manager_employee`, а не с текущим ответственным.

Администратор и управляющий могут сменить ответственного в карточке клиента или компании. Передача клиента меняет менеджера у всех его текущих и архивных заказов и позиций. Передача компании дополнительно меняет менеджера у связанных клиентов и у всех заказов компании. Комиссионный менеджер уже созданных заказов при этом не меняется.

## Расчётные листы и премии

В разделе зарплат администратору и управляющему доступна помесячная сводка менеджеров: количество и сумма заказов, оплаченная и неоплаченная часть, доля оплаты, средний чек и начисленный процент. Расчёты привязаны к `orders.commission_manager_employee`, поэтому передача клиента новому ответственному не переносит комиссию по старым заказам.

Расчётный лист формируется серверным endpoint `symbolika-profile/payslip` за выбранный месяц. Сотрудник может открыть только собственный лист в личном кабинете, администратор и управляющий — лист любого сотрудника из раздела зарплат. Лист можно распечатать или сохранить в PDF средствами браузера.

Премия хранится в `business_expenses` с типом `employee_bonus`, обязательной привязкой к сотруднику и обязательным основанием в `comment`. Премия считается одновременно начисленной и выплаченной: она входит в общую сумму начислений и выплат, но сама по себе не создаёт долг по зарплате. Как операционная выплата премия уменьшает финансовый результат месяца.

## Внутренняя передача между участками

Администратор и управляющий могут дополнительно направить конкретную позицию заказа в `Производство` и/или `Шелкографию`. Массового назначения маршрута всему заказу нет: каждый внутренний участок выбирается только в карточке нужной позиции. Маршрут хранится в `orders_items.internal_route_production` и `orders_items.internal_route_screen`. Эти флаги не меняют `contractor_1`, `contractor_2`, себестоимость и правила основной маршрутизации.

`sync_work_item()` добавляет позицию в `production_work` или `screen_printing_work`, если участок определён основным контрагентом либо включён соответствующий дополнительный внутренний маршрут. До запуска заказа в работу маршрут сохраняется, но позиция появляется в рабочей очереди участка только после перехода заказа/позиции в рабочий статус. Отключение дополнительного маршрута удаляет позицию только из дополнительной очереди; основной маршрут через контрагента продолжает действовать.

## Публичные ссылки и уведомления клиентов

У каждой позиции есть постоянный `public_token`. В Excel-выгрузке этикеток выводится публичная ссылка на позицию; сам QR-код система не рисует. Авторизованный сотрудник по ссылке попадает в рабочую карточку позиции, внешний посетитель видит только общую информацию, публичный статус, контакты менеджера и ссылки компании — без ТЗ, цен и внутренних данных.

Для клиента или компании выбирается один основной канал: email, ВКонтакте, Telegram, SMS либо `Не уведомлять`. Единственное автоматическое клиентское событие — заказ полностью готов и находится в офисе при способе получения `office_pickup`. Для доставки и иных способов получения внешние уведомления не отправляются.

## Уведомления сотрудников

Все внутренние уведомления сохраняются в `directus_notifications` и доступны сотруднику в отдельном модуле `Центр уведомлений`. Лента объединяет события заказов, позиций, задач, закупок и системные сообщения, поддерживает фильтры, прямой переход к связанному объекту и отметку одного или всех уведомлений прочитанными.

Штатный колокольчик Directus используется как единая точка входа и открывает `Центр уведомлений` вместо стандартной всплывающей панели. Системные уведомления Directus не копируются и не теряются: центр читает ту же таблицу `directus_notifications`, поэтому в одной ленте показываются как системные, так и рабочие события Символики.

Сотрудник отдельно выбирает состав ленты: статусы заказов, изменения позиций и макетов, новые задачи, изменения задач, производство, закупки, новые письма и финансы. Выбор событий не зависит от каналов доставки: сначала проверяется, нужно ли пользователю событие, затем оно отправляется в разрешённые им push, e-mail, VK или Telegram. Критические системные сообщения отключить нельзя. Новые письма по умолчанию выключены, остальные рабочие категории включены.

Персональные настройки каналов хранятся в `symbolika_employee_notification_settings`. Внутрисистемная история обязательна и не отключается; дополнительно сотрудник может включить browser push, e-mail, ВКонтакте и Telegram. Результат каждой внешней попытки хранится в `symbolika_employee_notification_deliveries`, поэтому сбой провайдера не блокирует основную автоматизацию и виден в ленте как ошибка доставки.

Сообщение содержит позиции, количество, цену и сумму, итог заказа, оплату и остаток, а также адрес и время работы офиса. Настройки офиса хранятся в `symbolika_customer_notification_settings`, журнал и защита от повторной отправки — в `symbolika_customer_notifications` с событием `ready_in_office`.

## Поддержка пилота и здоровье автоматизаций

Во всех рабочих модулях доступна кнопка `Сообщить об ошибке`. Endpoint `symbolika-support/report` автоматически прикладывает пользователя, URL, раздел, открытую сущность и данные браузера; сообщения хранятся в `symbolika_feedback_reports`. Администратор и управляющий видят их в `Управление -> Контроль автоматизаций` и меняют состояние обработки.

Незавершённый новый заказ сохраняется в `localStorage` отдельно для каждого пользователя. При повторном открытии системы в течение 30 дней предлагается восстановить поля заказа и позиций. Черновик удаляется только после успешного создания заказа или явного отказа пользователя.

Таблица `symbolika_automation_runs` хранит последнюю попытку, последний успешный запуск и последнюю ошибку обработчиков. Endpoint `symbolika-support/automation-health` выводит эти данные вместе с ошибками клиентских уведомлений. Безопасный повтор не меняет итоговые данные напрямую: контроль рассинхронизаций повторно запускает штатную функцию проверки, а уведомление проходит через тот же обработчик и его защиту от дублей.
